## Problem Statement

Zenny is currently built per-client inside Convocore (general-purpose visual
agent builder) + self-hosted n8n (execution) + Supabase (DB). Convocore's
multi-client management requires the White Label tier ($199/mo minimum,
confirmed live via Convocore's own support AI, 2026-08-25). One real
near-paying client (Carmelli Bakery, commerce-ecom archetype) is mid-onboarding
on this stack. The founder is deciding whether to replace Convocore with
Zenny's own conversation runtime, and if so, which of 4 candidate architecture
documents to build against — plus the bigger question of whether the current
scope (single-tenant-per-client builds on a general-purpose canvas) is the
right bet at all.

## Approaches Considered

### Approach A: Archetype-Reuse Probe (minimal viable, recommended by Claude — not chosen)

scaffolding (`agent_prompts`, `client_config`, tool tables already live from
the Convocore build) — swap Convocore's execution for a direct n8n AI Agent
node + LLM tool-calling. Onboard Carmelli plus one more client in the same or

Build the complete target-state architecture as documented: router +

## Recommended Approach

**Founder chose Approach B** (full MultiNode Runtime v1.0 + Channel Adapter
v2.0 build) over Claude's in-session recommendation of Approach A. No specific
reasoning was captured for overriding the recommendation — this is the
founder's call to make with context Claude doesn't have (e.g. a scale
ambition, a timeline commitment, or confidence in the archetype design from
having built all 6 templates already). Recorded here as a real decision, not
silently smoothed over.

**Consequence for sequencing:** since B is the full target-state build, the
"validate archetype reuse" question from revised Premise #3 does not get
answered by this build track on its own — it gets answered only once B is
live and a second client actually onboards onto an existing archetype using
the new runtime. Flagged as an Open Question below, not resolved by choosing B.

**Stop-gate control — corrected (Carmelli/Convocore dual-run mechanism no
longer applies; see CORRECTION section).** With Convocore fully stopped and
no live client to protect, the original "dual-run against Carmelli's
Convocore agent" design has nothing to run against — there's no fallback
system to keep live. The actual risk this session's diagnostic (Q4) flagged
— building an open-ended platform with no checkpoint — is addressed
differently now:
- **Milestone 1 (end of runtime build):** the runtime passes its own internal
  test suite (see Success Criteria's tightened metrics — human-judged,
  drawn from the commerce-ecom archetype's typical FAQ/order scenarios, not
  Carmelli-specific content since she's out of this loop) before the Channel
  Adapter build starts. This is an internal quality gate, not a real-client
  validation — real validation happens at launch (below).
- **Milestone 2 (before Channel Adapter build starts):** re-verify OpenBSP's
  project health live (commit activity, open issues, community size) since
  the Channel Adapter doc itself names this as a real risk (Section 4.5) —
  don't build against it on the strength of the doc alone, which is already
  months old by the time this milestone is reached.
- **Launch (real validation):** once both the runtime and channel gateway
  pass their internal milestones, launch means re-engaging the existing 7-8
  leads/day pipeline at the new, lower price point, across web chat +
  WhatsApp + Instagram together. The first real paying conversion off that
  pipeline is the actual market test this plan has been building toward —
  not a synthetic internal checkpoint.
- **No rollback system exists to fall back to** — this is now a from-scratch
  build toward a first production launch, not a migration off a running
  system. This simplifies the plan (no dual-run/shadow-mode complexity to
  build) but also means there is more real pressure to get Milestone 1 and 2
  right before launch, since there's no "stay on the old system a bit longer"
  safety net anymore.

**Architecture Review — 2 findings, both accepted:**
1. **Tenant isolation enforcement.** `app.current_org_id` being set correctly
   in every workflow can't rely on every workflow author remembering — one
   miss is a cross-tenant leak (this repo already had exactly this bug class
   once, BC-052's anon-grant exposure). **Fixed:** every conversation turn
   enters through one shared entry sub-workflow that sets
   `app.current_org_id` as its first node; individual node/tool workflows
   inherit it rather than setting it themselves — impossible to forget
   because it's structurally centralized, matching the existing "shared
   choke point" pattern this repo already uses (WF-017 as the shared
   Fallback-D destination for every Tool).
2. **LLM provider single point of failure.** OpenRouter now backs every
   conversation across every client. **Fixed:** a timeout + graceful
   degradation message — if the LLM call doesn't return in time, the customer
   sees a clear "having trouble right now" message instead of a silent hang.
