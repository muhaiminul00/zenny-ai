# Design: Admin Provisioning — Remove the Client-Picker Requirement from Add Admin

Generated by /plan-eng-review on 2026-09-02
Branch: main
Repo: muhaiminul00/zenny-ai
Status: APPROVED

## Problem

`control.dashboard_users` has one row per login, with `client_id uuid
NOT NULL` (FK to `control.clients`) — built for client accounts, where
"which client does this login belong to" is the whole point.
Admin/super_admin accounts don't belong to any client, but the shipped
Admin Provisioning Bootstrap card worked around the `NOT NULL`
constraint by requiring the admin creator to pick an arbitrary "nominal
home client" from a dropdown when minting an admin/super_admin account.
Human feedback after live-testing the shipped feature (2026-09-02):
"Add Admin" should just be email + temp password + tier, no client
picker — this is a schema wart, not intentional design.

## Live-verified facts (Mandatory MCP Verification)

- `dashboard_users.client_id`: `uuid NOT NULL`, FK to `control.clients`,
  zero RLS on the table (all access via `SECURITY DEFINER` RPCs +
  `REVOKE ALL` grants). `role` is separately `text NOT NULL` with its own
  CHECK constraint — no risk of a NULL `role` making the new CHECK
  evaluate to `UNKNOWN` (a concern Codex's outside-voice raised generally;
  checked and doesn't apply here).
- `dashboard_provision_user(p_auth_user_id, p_client_id, p_role)` does a
  plain `INSERT ... ON CONFLICT (auth_user_id) DO UPDATE SET client_id =
  EXCLUDED.client_id, role = EXCLUDED.role` — both columns are always set
  together, atomically, from whatever the caller passes. Verified: all 3
  Edge Function call sites (`map_existing`, `create_client`,
  `create_admin`) always pass a `(client_id, role)` pair that is
  internally consistent with the new CHECK constraint by construction —
  no caller ever mixes a real `client_id` with an admin-tier `role` or
  vice versa. `dashboard_provision_user` itself needs no code change.
- Audited all 6 live Postgres functions that read
  `dashboard_users.client_id`: `dashboard_get_my_client`,
  `dashboard_get_my_client_schema`, `dashboard_list_paused_recovery_leads`,
  `dashboard_release_lead_ownership` all `INNER JOIN` on it and are ONLY
  ever called from client-facing Dashboard routes (`App.tsx` never
  renders those routes for an admin-tier role) — a `NULL` `client_id`
  there just means "no row", already handled via `RAISE EXCEPTION`.
  `dashboard_provision_user` needs no change (see above).
- **Real, independent latent bug found during the audit:**
  `dashboard_admin_list_clients()`'s login-email lookup is
  `WHERE du.client_id = c.client_id ORDER BY du.created_at ASC LIMIT 1`
  with **no role filter** — it can pick an admin's row as if it were a
  client's "login" if an admin's (currently-required) `client_id` happens
  to match and is older than the client's real login. Confirmed live:
  exactly one admin-tier row exists today (`admin@zenny.internal`,
  `client_id` = Client A) — it currently avoids the bug only because
  Client A's real login (`test-dashboard-bc015@zenny.internal`, created
  2026-08-13) predates it by about 3 weeks. Timing luck, not correctness.
- Checked and confirmed **don't apply** (Codex outside-voice raised these
  as general risks; verified against this specific codebase):
  - No separate seed/dev/staging database exists for this project — one
    live Supabase project (`zenny-vault`), already fully audited above.
  - The Dashboard and Edge Function code use hand-typed interfaces
    throughout (`ClientRow`, `RequestBody`, `DashboardClient`, etc.) —
    zero usage of `supabase gen types typescript` / a generated
    `Database` type anywhere in the repo (confirmed via grep). No
    generated-type drift risk from the nullable column change.

## Decisions locked (human-approved via AskUserQuestion)

- **D1 — Strict CHECK constraint.**
  `CHECK ((role = 'client_user' AND client_id IS NOT NULL) OR (role IN
  ('admin','super_admin') AND client_id IS NULL))` — the schema itself
  states the real invariant (an admin never has a client), not merely
  permits NULL. Chosen over a lenient `role <> 'client_user' OR client_id
  IS NOT NULL` version that would allow future drift back toward the
  confusing state this fix removes.
- **D2 — Fix `dashboard_admin_list_clients()`'s role-filter gap in the
  same PR.** Add `AND du.role = 'client_user'` to the lateral join's
  `WHERE` clause — closes the real latent bug found during this fix's
  own audit, one-line change, already touching admin-row semantics here.
- **D3 — Backfill existing admin-tier rows' `client_id` to `NULL`.**
  Generalized per Codex's correction: `UPDATE control.dashboard_users SET
  client_id = NULL WHERE role IN ('admin', 'super_admin')`, not hardcoded
  to `admin@zenny.internal`'s email (only one row matches today, but the
  migration itself must be environment-safe, not fact-of-today-safe).
- **D4 (Codex correction, adopted directly) — migration step order.**
  `ALTER COLUMN ... DROP NOT NULL` → backfill `UPDATE` → `ADD CONSTRAINT`.
  Reversed order would fail immediately: `admin@zenny.internal`'s
  pre-migration row (`role='super_admin'`, `client_id` still set) would
  violate the strict CHECK the instant it's added, before the backfill
  ever runs.
- **D5 — Tab relabeling/grouping bundled into this PR.** Group "Add
  Client" + "Add Login (existing client)" under one visual section
  (both are about client accounts), keep "Add Admin" visually separated
  (a divider / "Internal accounts" header), tighten copy. Low regression
  risk (cosmetic), directly requested for "the same session."
- **D6 (cross-model tension, resolved) — defer the `useProvisionForm`
  hook extraction.** Originally decided to extract now; reconsidered
  after Codex's outside-voice specifically argued it triples this PR's
  regression surface (all 3 forms, not just Add Admin) in a repo with
  zero automated test coverage, for a fix whose real bug is schema-level.
  Human chose the split: keep D5's relabeling (cosmetic), defer the
  hook extraction to its own PR (logged in `TODOS.md`).
- **D7 (Codex correction, adopted directly) — explicit pairing
  regression test.** Live-verify `dashboard_provision_user`'s atomic
  `(client_id, role)` update by remapping `admin@zenny.internal` through
  `create_admin`'s own remap path post-fix and confirming `client_id`
  stays `NULL` — not just assumed safe from reading the function body.
- **D8 (Codex correction, adopted directly) — deployment note has 3
  steps, not 1.** Apply migration + function update (Supabase MCP) →
  deploy the updated Edge Function (Supabase MCP) → merge + restart the
  `zenny-dashboard` VPS container (same doctrine as every prior card).
  The original draft only explicitly named the container restart.
- **D9 (Codex correction, adopted directly) — rollback note.** Before
  the backfill (D3) runs, log the pre-backfill `client_id` value for
  every affected row (a `RAISE NOTICE` in the migration, or a saved
  `SELECT` result in `Wiki/log.md`) — a rollback to `NOT NULL` after the
  CHECK lands would otherwise require guessing which nominal client each
  admin used to have.

## Scope

- **1 Supabase migration** (`dashboard_users.client_id`): drop `NOT
  NULL` → backfill `role IN ('admin','super_admin')` rows to `NULL`
  (logging pre-backfill values first, D9) → add the strict CHECK
  constraint (D1).
- **1 Postgres function edit** (`dashboard_admin_list_clients()`): add
  the role filter (D2) — `CREATE OR REPLACE`, same signature/return
  type, no migration needed beyond the function body.
- **1 Edge Function edit** (`admin-provision-dashboard-user`,
  `create_admin` branch only): drop the `admin_client_id`/`client_id`
  read + validate + lookup block entirely; pass `p_client_id: null` to
  `dashboard_provision_user`. `map_existing` and `create_client` branches
  untouched.
- **1 Dashboard file** (`AdminProvision.tsx`): remove the client-picker
  field/state from `AddAdminTab`; regroup/relabel the 3 tabs (D5).

## NOT in scope

- **`useProvisionForm` hook extraction** (D6) — deferred to its own PR,
  logged in `TODOS.md` ("Extract a shared `useProvisionForm` hook for
  AdminProvision.tsx's 3 tabs").
- **Explicit role guards on the 4 client-only RPCs** — Codex flagged
  that they currently reject admin callers only incidentally (NULL join
  → no row → generic error), not via an explicit check. Security posture
  is already correct; this is a clarity/defense-in-depth improvement,
  logged in `TODOS.md` ("Client-only RPCs reject admin callers only
  incidentally, not explicitly"), not built here.
- **`dashboard_admin_list_clients()`'s "oldest client_user wins" policy**
  for a client with 2+ real logins — pre-existing ambiguity, unrelated to
  nullability, surfaced by this fix's own audit of the same lateral
  join. Logged in `TODOS.md`, not redesigned here.
- **`control.clients.status` lifecycle** and
  **`create_client_schema_from_template()` validation** — separate,
  pre-existing `TODOS.md` items, unrelated to this fix.
- **Any change to `map_existing` or `create_client`** Edge Function
  branches — both already pass consistent `(client_id, role)` pairs,
  verified, no change needed.

## Failure modes

| Failure | Test/verify | Error handling | User-visible? |
|---|---|---|---|
| Migration applies the CHECK before the backfill — `admin@zenny.internal`'s existing non-NULL `client_id` violates it immediately | Correct step order enforced in the migration script itself (D4) | Migration fails cleanly at apply time, before any live impact | No — caught at migration-apply time |
| `dashboard_provision_user`'s atomic update sets `client_id`/`role` inconsistently for some future caller | Live regression test (D7): remap `admin@zenny.internal` via `create_admin`, confirm still `NULL`+`super_admin` after | All 3 current Edge Function call sites already pass consistent pairs by construction — verified, not assumed; the strict CHECK (D1) is the backstop if a future caller ever gets this wrong | Would surface as a clean Postgres constraint violation, not silent data corruption |
| `dashboard_admin_list_clients()`'s role-filter edit breaks the existing client list for real clients | **CRITICAL — IRON RULE regression test.** Live PostgREST re-verification against all 6 real clients, same doctrine as this function's 2 prior live bugs (archetype_enum cast, varchar/text cast) | N/A — this is the primary verify step for T2 | Yes — a broken picker/list would silently misrender or 500 |
| Rollback needed after the CHECK/backfill land | Pre-backfill `client_id` values logged (D9) before nulling | Rollback would otherwise require guessing nominal client values per admin row | N/A unless rollback is needed |

## Worktree parallelization strategy

Sequential — all changes touch the same live Supabase project, the same
Edge Function, and the same `AdminProvision.tsx` file. No independent
workstreams to split across worktrees.
