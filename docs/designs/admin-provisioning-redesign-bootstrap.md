# Design: Admin Provisioning Bootstrap

Generated by /office-hours on 2026-09-02
Branch: main
Repo: muhaiminul00/zenny-ai
Status: APPROVED
Mode: Startup

## Problem Statement

BC-076-Card2a shipped `/admin/provision`, but it only maps a dashboard
login to a `control.clients` row that **already exists**. There is no
admin-UI path to actually create a new client, no visibility into which
clients are mid-onboarding vs. live, and any `role='admin'` account can
mint another admin with no extra gate (logged, accepted risk in
`TODOS.md`).

## Status Quo

Today, provisioning a new dashboard user means: an admin picks an
existing client from a dropdown, sets a role (`client_user` or
`admin` — same dropdown, no distinction in who can pick which), and the
Edge Function creates the Auth user + mapping. Creating the *client*
itself (the `control.clients` row, and the real per-client schema
cloned from a `tpl_*` archetype template) happens outside this UI
entirely — undocumented as an automated process anywhere in this repo.

## Premises

1. The real gap isn't the form's UX — it's that client *creation* has
   no UI path, and schema-cloning is the actual bottleneck.
2. Splitting "Add Client" / "Add Admin" into separate tabs doesn't by
   itself close the admin-minting risk — it relocates the button.
   **Revised during session:** a real `admin` / `super_admin` tier,
   gating who can even see the Add Admin tab, closes it for real.
3. A client status field (`onboarding`/`demo`/`active`) is new schema
   (a column + an enum on `control.clients`) — needs a live check
   (Mandatory MCP Verification) for whether a status-shaped column
   already exists before assuming it doesn't.
4. **Key insight, from the human directly:** you cannot pick a client's
   archetype before the client tells you what their business is. This
   means schema-cloning **cannot** happen at admin-bootstrap time no
   matter which approach is chosen — the archetype has to come from the
   client's own onboarding answers, later. This collapses what looked
   like a 3-way architecture fork into two genuinely separate pieces of
   work: (a) admin bootstraps a login + status row now, (b) a client-
   facing onboarding flow decides the archetype and triggers real
   provisioning, as its own later effort.

## Approaches Considered

### Approach A: Bootstrap only, provisioning stays manual
Add Client tab (email + admin-set temp password → Auth user +
`control.clients` row, `status='onboarding'`, `archetype=NULL`,
duplicate-email checked before creating) + a client list (email,
client name, status, created_at) + Add Admin tab gated by a new
`super_admin` tier. Schema-clone stays a manual/scripted step, same as
today. Client's first login forces a password change (new requirement,
not present in Card2a's flow — that flow only ever showed an
admin-facing password once, never a client-facing first-login gate).
Password delivery is the same disclosed pattern Card2a already uses:
shown once to the admin, who relays it to the client out-of-band
(email/chat) — not a new mechanism, no in-app email-send added by this
card. Effort **S/M** (bumped from a first-pass S — this revision added
a server-side tier gate, an audit column, a forced-reset flow, and an
RLS review pass, more surface than "extends the Edge Function" alone
implies), **extends** Card2a's Edge Function — new branching logic, not
straight reuse: Card2a's function maps a login to an *already-existing*
client; this path additionally creates the `control.clients` row in the
same call, a two-system write (Supabase Auth + Postgres) Card2a never
had to compensate for. Con: self-serve half isn't real — a client still
needs an admin to manually finish their tenant.

**Security requirement, not optional:** the `super_admin` gate must be
enforced **server-side**, inside the Edge Function/RPC that creates an
admin — checking the caller's own tier, never a body-supplied flag.
Hiding the Add Admin tab client-side is UX only, same disclosed
UI/server split Card2a already established; it does not by itself close
the accepted risk in `TODOS.md`. Log who created each client/admin
(`created_by` on the new row) — this is a privilege-escalation-adjacent
feature and currently has no audit trail at all.

Status transitions (`onboarding` → `active`) are explicitly **not**
this card's job — ownership moves to Approach B (below) once it exists;
until then a client can sit in `onboarding` indefinitely, which is
correct, not a bug, for this scope.

### Approach B: Full self-serve loop, schema clone included
Everything in A, plus a new client-facing onboarding page (post-login)
where the client picks their own archetype + config, and submitting it
auto-drives the real schema clone. Effort L — first time this project
would automate live DDL from a user action; needs its own careful
review, not foldable into a panel-cleanup pass.

### Approach C (chosen — see below)
A now; B logged as a separate, explicitly-scoped follow-up rather than
guessed at or silently absorbed.

## Recommended Approach

**Approach C**, human-selected. Ship exactly Approach A as the next
Build Card. Track the client-driven onboarding + auto-provisioning
loop (Approach B) as its own future item — real scope, not yet
designed at the RPC/schema level, deliberately deferred rather than
rushed into this pass.

## Open Questions

- Does `control.clients` already have a status-shaped column? (Live
  Supabase check — Mandatory MCP Verification, not decided here.)
- Exact `super_admin` gate mechanism: a new `dashboard_users.tier`
  column, or reuse/extend the existing `role` check constraint to a
  3-value enum (`client_user`/`admin`/`super_admin`)? Live check needed
  on how `role` is read elsewhere before choosing.
- Bootstrap-of-the-first-super_admin: same manual-provisioning pattern
  as the very first admin in Card2a, or promote the existing
  `admin@zenny.internal` account directly?
- **Blast radius of extending `role` to a 3rd value:** everywhere
  `role` is read today (RLS policies, the existing CHECK constraint,
  `dashboard_get_my_role()`, any client-side branch on `role==='admin'`)
  needs a live check for code/policy that assumes exactly two values —
  not just "does the column allow it."
- Does Card2a's orphaned-user rollback pattern actually cover this
  card's new failure mode (Auth user created, but the `control.clients`
  insert fails)? Card2a's rollback only ever had to undo a *mapping*
  failure against an existing client — this is a genuinely new
  compensating-transaction case, not a proven-identical reuse.
- RLS on `control.clients`/`dashboard_users` needs an explicit review
  pass once the new columns/tier exist — not assumed safe by default,
  per this project's own postgres-best-practices standing guidance.
- **Forced-password-reset mechanism is unspecified.** Supabase Auth has
  no native "must change password" flag — this likely needs a
  `must_change_password`-shaped column (or Auth `user_metadata` field)
  checked by the dashboard's own login route. Needs a live check on
  what Supabase Auth actually exposes here before assuming the shape,
  same as the other schema Open Questions above.

## Success Criteria

- Admin can create a new client (login + status row) through the UI
  without touching Supabase directly.
- A non-`super_admin` caller is rejected **server-side** by the Edge
  Function/RPC itself when attempting to create an admin — not merely
  hidden from the tab client-side (tested directly, same as Card2a's
  negative-case curl tests).
- Client status is visible in a real list view (email, client, status,
  created_at), not just implied.
- Every new client/admin row records who created it.

## Dependencies

None blocking — extends Card2a's Edge Function and RPCs (new branching
logic, not a drop-in reuse — see Approach A). Approach B (deferred)
depends on this shipping first.

## Plan-Eng-Review Findings (2026-09-02) — resolves all Open Questions above

**Live verification (Mandatory MCP Verification), not guessed:**

1. **Status column already exists with the exact value needed.**
   `control.clients.status` is `client_status_enum`
   (`active`/`paused`/`onboarding`/`offboarded`) — no migration for this
   part. **But**: every existing client (5 test clients + the real demo
   client, Carmelli Bakery) sits at `status='onboarding'` — nothing has
   ever transitioned status to `active`. A shell client would be
   indistinguishable from a working one in a status-based list view.
   **Decision (D1):** add a new enum value, `unprovisioned`
   (`ALTER TYPE client_status_enum ADD VALUE 'unprovisioned'`), used
   only for Add-Client shell rows; transitions to `onboarding` once
   archetype+schema exist (matching today's meaning). The deeper
   lifecycle gap (nothing ever sets `active`) is real but pre-existing
   and bigger than this card — logged in `TODOS.md`, not fixed here
   (**D2**, human-confirmed after Codex's outside-voice challenge).

2. **`control.clients.archetype` and `.client_schema_name` are both
   `NOT NULL`** — a genuine blocker for Approach A's original "shell
   row, archetype=NULL" plan, found live. **Decision (D3):** loosen both
   to nullable; every RPC reading these columns must be audited for
   NULL-safety before shipping (see T-tasks below).

3. **`dashboard_users.role` is `text` with a CHECK constraint**
   (`role = ANY (ARRAY['client_user','admin'])`), not a Postgres enum
   type — extending to `super_admin` is a cheap constraint replace, not
   a type migration. **Zero RLS policies exist** on `control.clients` or
   `control.dashboard_users` (access is entirely via SECURITY DEFINER
   RPCs + REVOKE ALL grants) — extending `role` has zero RLS blast
   radius. **Blast radius resolved:** exactly 3 client-side call sites
   read role (`App.tsx:68`, `App.tsx:111`, `AdminProvision.tsx:55`),
   all locatable and small to update.

4. **MAJOR FINDING, changes the record:** `public.
   create_client_schema_from_template(p_archetype, p_specific_tables,
   p_client_schema)` **already exists live** — it clones a `tpl_*`
   template schema into a new client schema (tables, FKs, RLS, grants).
   The design doc's Status Quo section's claim that schema-cloning
   automation "doesn't exist anywhere in this repo" is **false**. It has
   **zero callers anywhere** and has never run against a real client
   (none of the 6 existing clients were provisioned through it) — dead,
   unverified infrastructure, not a productized path. Not `SECURITY
   DEFINER`, so it needs a privileged caller (service_role) to run at
   all. Logged in `TODOS.md` as needing validation before anything
   trusts it.

5. **Forced-password-reset mechanism:** Supabase Auth has no native
   flag for this. **Decision (D4, resolved via BC-051 precedent, not
   re-asked):** a `must_change_password boolean` column on
   `dashboard_users` — colocated with `role`/tier, consistent with
   BC-051's own established reason for moving identity data off Auth
   `user_metadata` onto this table in the first place.

**Architecture Issues raised interactively (all resolved, human-confirmed):**

- **Issue 1 (D3 above):** loosen `archetype`/`client_schema_name` to
  nullable + audit consumers, over admin-picks-archetype-now or
  stage-in-a-separate-table alternatives.
- **Issue 2 (D1 above):** add `unprovisioned` enum value, over a
  separate boolean column or shipping without a real distinction.
- **Issue 3 (write ordering):** for the 3-system write (control.clients
  row → Auth user → dashboard_users mapping), write the client row
  FIRST (cheap rollback, plain DELETE), then Auth user (rollback:
  delete client row), then mapping (rollback: delete both, reusing
  Card2a's existing Auth-delete pattern) — minimizes what a failure
  needs to clean up, over Card2a's original Auth-first ordering.

**Code Quality Issue raised (resolved, human-confirmed):**

- Extend the existing `dashboard_admin_list_clients()` RPC with
  status/created_at/email rather than adding a parallel RPC — DRY, per
  the human's stated preference. **Regression risk flagged as
  CRITICAL per the Iron Rule:** this RPC's return shape was already the
  site of a real live bug once (the `archetype_enum`-vs-`text` cast
  mismatch from Card2a, caught only by browser testing) — the existing
  client-picker caller in `AdminProvision.tsx` MUST be re-verified after
  this change, not just the new list view.

**Outside Voice (Codex, `ready` mode, high reasoning) — 2 substantive
cross-model tensions, both resolved with human sign-off:**

- **Tension 1:** should "Add Client" provision the real schema
  immediately when the admin already knows the archetype, given the
  clone function exists? **Resolved: keep shell-only for this card**
  (option B) — the clone function is "untrusted legacy infrastructure
  until exercised... its existence reduces discovery risk, not
  implementation risk" (Codex's own words); wrapping it safely is real,
  separate work, not smuggled into this admin-panel card.
- **Tension 2:** does adding `unprovisioned` actually fix the status
  lifecycle, given nothing ever sets `active`? **Resolved: D2 above** —
  logged as its own TODO, not fixed in this card.
- Smaller Codex refinements adopted directly (not contested, no tension
  needed): the `super_admin` gate must protect every privileged
  admin-mutating action (create client, create admin), not just "Add
  Admin" specifically; `must_change_password` must be enforced before
  any privileged dashboard action, not just shown once at login.

- `create_client_schema_from_template()` is untested, unverified
  infrastructure — validate before anything trusts it.
